👥 1. Actors

In a SaaS multi-tenant model, actors exist at two layers: Platform Layer (cross-tenant operations managed by the SaaS provider) and Tenant Layer (within a single subscribing organization).

Tenant / L&D Admin Tenant Primary Manages org's instance: users, risk rules, integrations, compliance reports UC-04, UC-05, UC-09, UC-10, UC-13

📋 3. Use Case Specifications

🟪 Platform-Level Use Cases (SaaS)

UC-01 | Tenant Self-Service Onboarding  SaaS Platform

Actor:L&D Admin (new organization), Super Admin (oversight)
Precondition:Organization has a valid email domain; no existing tenant for this domain
Main Flow:
  1. L&D Admin visits the SaaS portal and clicks "Register Organization"
  2. Admin enters: org name, domain, admin email, and selects subscription tier
  3. Platform provisions isolated tenant environment (DB schema, API keys, config)
  4. Admin receives verification email; confirms email address
  5. Admin completes setup wizard: user import, SSO config, integration setup
  6. Tenant is marked "Active"; Super Admin receives new tenant notification
Alternate Flow:Domain already registered → show error "Organization already exists"
Postcondition:Tenant is fully provisioned and active with isolated environment

UC-02 | Super Admin Manages Tenant  SaaS Platform

Actor:Super Admin
Precondition:Super Admin logged into platform admin portal
Main Flow:
  1. Super Admin views tenant list with: status, tier, active users, last activity
  2. Super Admin can: suspend tenant, upgrade/downgrade tier, reset admin password, impersonate for support (audit-logged)
  3. All Super Admin actions are recorded in platform audit trail
  4. Super Admin views platform-wide health metrics and usage dashboards
Restriction:Super Admin cannot view employee-level data within tenant without explicit support request and consent
Postcondition:Tenant state updated; audit record created for every action

UC-03 | Manage Subscription Tier  SaaS Platform

Actor:L&D Admin (tenant), Super Admin
Precondition:Tenant is active; billing system integrated
Main Flow:
  1. Admin navigates to Subscription settings within tenant portal
  2. Admin views current plan, usage metrics (employees, API calls, storage)
  3. Admin selects new tier (upgrade or downgrade)
  4. Platform enforces new limits immediately on upgrade; on downgrade, current period continues
  5. Billing system (Stripe/Chargebee) is notified via API; invoice generated
  6. Confirmation email sent to tenant admin
Alternate Flow:Usage exceeds tier limit → System warns admin; blocks feature access until upgraded
Postcondition:Tenant subscription updated; features enforced per new tier

UC-04 | Configure Tenant SSO  SaaS Platform

Actor:IT Administrator (tenant)
Precondition:Tenant is on Professional or Enterprise tier; IT Admin has IdP metadata
Main Flow:
  1. IT Admin navigates to Security → SSO Configuration within tenant settings
  2. Admin selects protocol: SAML 2.0 or OIDC
  3. Admin uploads IdP metadata / enters OIDC config (client ID, secret, discovery URL)
  4. Platform validates SSO configuration via test authentication
  5. SSO is activated; users are redirected to org's IdP on login
  6. Fallback: local password login disabled for SSO-enabled tenants (configurable)
Postcondition:All tenant users authenticated via org's Identity Provider

🟦 Tenant-Level Use Cases (Functional)

UC-05 | Ingest Employee Training Data

Actor:External System (per-tenant API), IT Admin
Precondition:Tenant API key configured; source systems available
Main Flow:
  1. External system sends POST request with per-tenant API key in header
  2. Platform validates: API key → resolves to tenant context
  3. Rate limiter checks request count against tenant's tier quota
  4. Payload validated (schema, completeness, data types)
  5. Valid records stored with tenant_id tag (RLS enforced)
  6. Profile aggregation job triggered for affected employees
Alternate Flow:Rate limit exceeded → HTTP 429 Too Many Requests; tenant admin notified
Postcondition:Tenant's employee profiles updated with latest data

UC-06 | View Employee Learning Profile

Actor:L&D Admin, Trainer, Manager (team only), Employee (own only)
Precondition:User authenticated in tenant context; employee data ingested
Main Flow:
  1. User navigates to Employee Profiles within their tenant
  2. RLS ensures only records with matching tenant_id are returned
  3. System returns aggregated profile: attendance %, scores, milestone status, risk level
  4. User drills down into individual records; trend charts rendered
  5. Intervention history shown if role permits
Postcondition:User views comprehensive, tenant-scoped learning profile

UC-07 | Configure Risk Rule (Tenant-Scoped)

Actor:L&D Administrator
Precondition:Admin logged into tenant; rule count within tier limit
Main Flow:
  1. Admin opens Risk Rules panel (tenant-scoped); sees existing rules and global templates
  2. Admin can: create from scratch, or clone from global template library
  3. Admin defines: rule ID, name, severity, conditions, actions, applicable roles
  4. System validates rule syntax and checks tier limit (e.g., Basic = max 5 rules)
  5. Rule saved with version number and tenant_id; audit record created
  6. Admin activates rule; applied in next nightly risk evaluation cycle
Alternate Flow (Tier Limit):Basic tier at 5 rules → "Upgrade to Professional for unlimited rules" prompt
Postcondition:Rule active for this tenant only; no effect on other tenants

UC-08 | Identify At-Risk Learners (Automated)

Actor:System (automated daily batch), L&D Admin, Trainer
Precondition:Risk rules active per tenant; employee profiles available
Main Flow:
  1. Nightly batch job runs per tenant (staggered to manage platform load)
  2. For each employee, all active rules for that tenant are evaluated
  3. Composite risk score calculated; risk level assigned (Critical/High/Medium/Low)
  4. Risk record created with tenant_id; alerts dispatched to trainer and L&D Admin
  5. At-risk employees appear on Trainer and Admin dashboards
  6. Notification channel per tenant tier: email (Basic); email+SMS+in-app (Pro/Enterprise)
Postcondition:At-risk learners flagged; stakeholders notified within tenant context

UC-09 | Assign Intervention

Actor:Trainer, L&D Admin
Precondition:Employee flagged at-risk; Trainer authenticated in tenant
Main Flow:
  1. Trainer views at-risk profile and selects "Assign Intervention"
  2. System recommends intervention types based on triggered rules
  3. Trainer selects type (remedial / coaching / mentoring), sets schedule and resource
  4. Intervention record saved with tenant_id; submitted for approval
  5. L&D Admin or Manager approves or rejects with reason
  6. On approval: employee and manager notified; status = "Active"
Postcondition:Intervention active and tracked within tenant context

UC-10 | Track Intervention Effectiveness

Actor:Trainer, L&D Admin
Main Flow:
  1. System captures pre-intervention baseline (attendance %, score, milestone status)
  2. Trainer marks session attendance after each session
  3. On completion, system fetches latest profile metrics as post-intervention data
  4. Improvement % and statistical significance calculated and stored
  5. Outcome visible in Intervention Effectiveness report and dashboard
  6. If no improvement: risk flag remains active; escalation alert sent
Postcondition:Intervention outcome recorded and available for reporting within tenant

UC-11 | Generate Compliance Report

Actor:L&D Admin, Compliance Officer
Main Flow:
  1. User selects report type from tenant's report module
  2. Configures parameters: date range, department, format (PDF/Excel/CSV)
  3. System aggregates only tenant-scoped data (RLS enforced)
  4. Report generated; audit log entry created (tenant-scoped)
  5. Report downloaded or scheduled for auto-distribution
Postcondition:Compliance report generated, audit-logged, available for regulatory use

UC-12 | View Role-Based Dashboard

Actor:All authenticated tenant users
Main Flow:
  1. User logs in (via SSO or local auth) to their tenant portal
  2. System renders role-appropriate dashboard with tenant-scoped data only
  3. Dashboard widgets vary by subscription tier (Basic shows limited widgets)
  4. User applies filters and drills down into metrics
Postcondition:User has real-time, role-filtered, tenant-scoped visibility

Flow 3: Multi-Tenant Data Isolation (RLS)

User (Tenant A) requests employee list
        │
        ▼
Authentication → JWT contains: user_id, tenant_id, role
        │
        ▼
API resolves tenant_id from JWT
        │
        ▼
Database query: SELECT * FROM employees WHERE tenant_id = 'TENANT_A'
        │  (Row-Level Security enforced at DB level)
        ▼
Result: Only Tenant A employees returned
        │
        ▼
Tenant B user making same request → receives ONLY Tenant B data
(zero cross-tenant data leakage at any layer)

Flow 4: Subscription Tier Enforcement

L&D Admin (Basic tier) tries to create 6th risk rule
        │
        ▼
System checks: tenant tier = BASIC, rule_count = 5, limit = 5
        │
        ▼
Request BLOCKED → UI shows:
"Basic tier allows up to 5 rules.
 Upgrade to Professional for unlimited rules."
        │
        ▼
Admin clicks "Upgrade" → Subscription flow triggered
→ Billing updated → New tier enforced immediately
→ Rule creation now permitted
